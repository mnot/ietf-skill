# Application features in the DNS — RFC 6950

**Text:** `rfc6950.txt`

## Does it fire?

The draft puts data into the DNS, takes data out of it, or reads the existence of a name as a
protocol signal. Requiring an operator to publish a record — even an empty one — counts.

## Where to look

- **§5** — principles and guidance, including the list of indicators that the DNS is not the right
  tool for a feature. The section most reviews cite.
- **§2.1** — naming conventions as a substitute for resource records, and why they carry less than
  a record type does.
- **§3.3, §3.3.1** — metadata about tree structure, and records whose only job is to predict
  whether a later query will succeed.

## What this lens asks

- What is being asked of the DNS, and could an application-layer mechanism carry it instead?
- Does the design require a name whose administrative owner is not the party who benefits?
- Is name existence being used as a boolean, and has the draft accounted for negative caching?
- Does the data need selective disclosure, or freshness the DNS does not offer?

## Firing, versus only looking like it

**This lens often comes back supporting the design.** §5's conclusion favours moving rich
application features out of the DNS and into application protocols, so a draft that deliberately
puts key material behind HTTPS rather than in DNS records is doing the recommended thing. Recording
that is more useful to a reviewer than most nits, because it is what stops a run of findings
reading as an attack on the approach.

Where it does fire, the finding is usually narrower than "do not use the DNS" — it is that a
particular use is misaligned: an identifier whose administrative model does not match the tree, or
a record inserted only to make a later lookup behave.

## What it does not cover

Whether the DNS names chosen intrude on someone else's namespace — that is RFC 8820.
