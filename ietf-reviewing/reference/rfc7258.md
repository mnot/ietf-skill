# Pervasive monitoring — RFC 7258

**Text:** `rfc7258.txt`

Short document; you can read the whole thing in the time it takes to locate a section.

## Does it fire?

The design creates or widens a vantage point from which many users' activity can be observed —
*indiscriminately and at large scale*. The scale qualifier is the whole test, and it is what most
often keeps this lens from firing.

## Where to look

- **§1** — the definition, and the scale qualifier that bounds it. Read the qualifier before
  deciding this lens fires; it is what rules most candidates out.
- **§2** — the obligation: if asked, the work needs a good answer to whether pervasive monitoring
  is relevant and how it was considered.

## What this lens asks

- Does the design let one party observe many users, or one user more thoroughly?
- Is the observation a by-product of the architecture, or does someone have to choose to collect?
- If the draft raises pervasive monitoring as an argument *against* an alternative, has it turned
  the same analysis on itself?

## Firing, versus only looking like it

Almost any protocol creates *some* observation point, so the pull toward firing is constant and
usually wrong. Two things distinguish a real hit: the observer is not a party the user chose to
contact, and the exposure is bounded only by the deployment's size. A first-party disclosure to a
server you deliberately connected to is not pervasive monitoring, however sensitive. Neither is an
exposure confined to one administrative domain.

Where the lens fires weakly, RFC 6973 usually carries the finding better, and citing both is
padding. Say so in the result rather than citing thinly.

## What it does not cover

Targeted interception, which is RFC 2804, and per-party data exposure, which is RFC 6973.
