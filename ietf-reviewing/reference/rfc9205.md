# Building protocols with HTTP — RFC 9205 (BCP 56)

**Text:** `../../ietf-http/reference/rfc9205.txt`

The `ietf-http` skill carries this text, along with RFC 9110 (semantics), RFC 9111 (caching) and
RFC 8820. If that skill is available, load it — it goes well beyond this lens.

## Does it fire?

The draft defines an application that uses HTTP: an https URL, a method, a status code, a header field, a media type, or a well-known URI registration.

Read §1 and §2 before anything else. RFC 9205 puts generic HTTP extensions outside most of its requirements, and an httpbis draft is very often exactly that. Where the draft is a generic extension, only §4.7 (defining a field, which routes on to RFC 9110 §16.3.2) and §4.16 (extension mechanisms) have a target; the rest of §4 has none.

## Where to look

This is the densest lens in the set; go by what the draft does.

- **§1, §2** — the scope limits, and which of the two classes this draft is in. Settle that before applying anything in §4; §2 also says the full HTTP requirements apply regardless.
- **§4.1** — using HTTP as the primary reference, and showing complete request and response
  messages. A draft with no HTTP examples usually has other gaps too.
- **§4.3** — client behaviour, including specifying that TLS certificates are checked.
- **§4.4, §4.4.1** — URL structure, and when a well-known URI is the right pattern. §4.4 defers the
  general question to RFC 8820.
- **§4.6, §4.6.1** — status codes, and specifying when redirects are followed.
- **§4.8** — media types: register one per format defined.
- **§4.9, §4.9.1, §4.9.3** — caching, heuristic freshness, and whether a response must be fresh at
  the point of use.
- **§4.13** — coexisting with browsers, including content-type sniffing and referrer policy.
- **§4.14** — allowing multiple applications on an origin.

## What this lens asks

- Does the document say what the response *is* — status codes, media type, freshness — or only
  what the request looks like?
- What does a client conclude from each class of failure, and is "not found" distinguishable from
  "could not ask"?
- Are new formats given registered media types, or served as `application/octet-stream`?
- Is anything generic to HTTP being re-specified here?
- Are the resources reachable by a browser, and does the document account for that?

## Firing, versus only looking like it

A generic HTTP extension is not an application. The fire test above catches every one of them, so the §1/§2 check is the only thing standing between this lens and a set of findings against requirements RFC 9205 disclaims for that class of document. Get it wrong and the findings look well-grounded — they cite real sections — and are worthless.

The most common finding is silence rather than error: a draft specifies a request and says nothing
about the response. Silence still needs quoting — quote the one sentence that does describe the
response, and show the search that found nothing else.

Do not raise a well-known URI *path* prefix as a problem: §4.4.1 explicitly sanctions putting an
application's resources under one, and RFC 8820 §2.3 names it as the exception.

## What it does not cover

URI authority and query structure, which is RFC 8820 — a draft that trips this lens on URLs usually
needs both.
