# Extension viability — RFC 9170

**Text:** `rfc9170.txt`

## Does it fire?

The draft defines *or registers into* an extension point. The question this lens asks is not
whether the point exists but whether it will still work the first time someone needs it.

## Where to look

- **§3** — active use, and the argument that availability of a capability is assured only by using
  it. The section most often cited.
- **§2.2, §2.3** — how extension points fall into disuse, and what that costs later.
- **§3.2** — version negotiation specifically.
- **§4.1, §4.2** — fewer extension points, and invariants. Both can *support* a design: reusing one
  extension point for core elements and extensions is the recommended pattern, and a declared
  invariant with a verification rule is good practice.

## What this lens asks

- Is the extension mechanism used by anything today, including by the document itself?
- If a value or version arrives that an implementation has not seen, what happens — and has anyone
  ever tested that path?
- Does the design add an extension point that nothing will exercise until it is urgently needed?

## Firing, versus only looking like it

This lens frequently produces a *supporting* result rather than a concern, and that is worth
recording: a document that exercises its own extension point, or that declares an invariant and
says how to check it, is doing what RFC 9170 recommends.

Where it does produce a concern, check whether RFC 6709 states the same thing more directly —
§4.1 on under-specified versioning usually does. Two citations on one paragraph is padding; pick
the one that tells the authors what to change.

## What it does not cover

Whether the extension point is well designed or properly registered — that is RFC 6709.
